# Конфигурация nginx на боевом сервере

Лежит здесь, чтобы не потерялась и разворачивалась воспроизводимо.
На сервере файлы находятся в `/etc/nginx/`.

| Файл | Куда класть |
|---|---|
| `new.imbir.dev.conf` | `/etc/nginx/sites-available/new.imbir.dev` + симлинк в `sites-enabled/` |
| `cloudflare-realip.conf` | `/etc/nginx/conf.d/cloudflare-realip.conf` |

## Почему X-Forwarded-For перезаписывается, а не дописывается

Стандартный `$proxy_add_x_forwarded_for` СКЛЕИВАЕТ значение, присланное
клиентом, со своим. Приложение берёт первый элемент списка — то есть тот,
что подконтролен клиенту. На этом ограничение частоты обходилось полностью:
достаточно слать новый `X-Forwarded-For` в каждом запросе, и лимит 5/мин
не срабатывает никогда (проверено живьём: 8 запросов, 0 блокировок).

Поэтому здесь `proxy_set_header X-Forwarded-For $remote_addr;` — перезапись.
Дополнительно `lib/rate-limit.ts` предпочитает `X-Real-IP`, который прокси
тоже перезаписывает.

## Зачем cloudflare-realip.conf

Когда перед сайтом включено проксирование Cloudflare, `$remote_addr` равен
адресу Cloudflare, а не посетителя — ограничение частоты стало бы общим на
всех. Модуль real_ip подменяет `$remote_addr` на значение `CF-Connecting-IP`,
но доверяет ему только если запрос действительно пришёл из диапазонов
Cloudflare.

Диапазоны обновляются редко; актуальные — на
https://www.cloudflare.com/ips-v4 и https://www.cloudflare.com/ips-v6

## Защита через Cloudflare

Порядок включения (менять местами нельзя):

1. **DNS.** В Cloudflare, домен `imbir.dev`, запись `new` типа A →
   `185.129.51.231`, облачко **серое** (DNS only).
2. **Сертификат.** На сервере: `certbot --nginx -d new.imbir.dev`.
   При оранжевом облачке выпуск не пройдёт — проверку перехватит Cloudflare.
3. **Проксирование.** Переключить облачко на **оранжевое**.
4. **Режим SSL** в Cloudflare: **Full (strict)**. Не «Flexible» — иначе
   участок Cloudflare → сервер пойдёт без шифрования.
5. **Замок.** Запустить `deploy/lock-to-cloudflare.sh` — после него сервер
   принимает 80/443 только из сетей Cloudflare, обратиться к нему напрямую
   по IP нельзя. Так же закрыт `sert.imbir.kz`.

Пока шаг 5 не сделан, защиту Cloudflare можно обойти прямым обращением к
IP-адресу — фильтрация ботов и ограничение запросов на уровне Cloudflare
просто не увидят такой трафик.

Модуль real_ip (см. `cloudflare-realip.conf`) нужен независимо от замка:
без него `$remote_addr` равен адресу Cloudflare и ограничение частоты
в приложении становится общим на всех посетителей сразу.
